# observability

Production is where this code will fail. Review whether an on-call engineer who
has never seen this code could see it fail, find the one request, follow it
across services and know why, from the telemetry alone, without the telemetry
itself leaking data, costing too much or taking the app down.

## Review

- **boundary-signal**: Every new entry point (HTTP route, queue or event consumer, scheduled job, worker, CLI command) and every call that leaves the process (HTTP, database, cache, queue, model API, file or shell) runs inside a span, from framework instrumentation or the repository's tracing helper. Flag: a new route, consumer, job or outbound call outside any span. Why: an outage there is invisible.
- **context-propagation**: Trace context crosses every boundary the work does. Outbound HTTP goes through an instrumented client, a published message carries the context in its headers and its consumer continues or links it, and deferred work (a timer, an in-process queue, a fire-and-forget promise, `waitUntil`) runs inside the span that started it. Flag: a hand-built client that bypasses instrumentation, a message published without context, a consumer that starts a fresh root, a detached promise. Why: the trace breaks at the boundary, and so does the investigation.
- **error-context**: A caught or rethrown error keeps its cause (`new Error(msg, { cause })`), is recorded on the active span with status ERROR, and is logged once with the identifiers that find the request: ids, never payloads. Flag: an empty `catch`, a rethrow of a bare message, a log of `error.message` without the error, an error turned into a success response with no record, the same error logged at every layer. Why: the trail ends at the catch.
- **structured-logs**: Server code logs through the repository's structured logger with fields, at a level that matches what happened, and every line carries the trace and span id. Flag: interpolated log strings, `console.log` in server code, a second logger, a logger not wired to the trace, an error logged at info. Why: nobody can search, alert on or jump from a line of prose.
- **request-context**: A handler or job puts the bounded identifiers that find one request on its span or request-scoped logger (the wide event): tenant, user, order or job id, the outcome. A change that adds a decision to existing code (a branch, fallback, retry, cache hit or miss, flag variant, or a choice between providers or rules) records which way it went there, as a bounded value. Flag: a new handler whose span carries nothing beyond its route, or a new path through existing code that leaves no trace of having been taken. Why: the trace says what failed, not for whom or which way the code went.
- **no-sensitive-data**: Logs, span attributes, events and metric labels carry no secrets, tokens, passwords, cookies, whole request bodies or headers, or personal data beyond the ids the team has agreed to keep. Flag: logging a whole object built from user input, headers or credentials; an email, name, address or card field as an attribute. Why: telemetry becomes the leak.
- **silent-drop**: Code that skips, filters or discards records, gives up on a retry, times out, or falls back counts or logs what it dropped and why. Flag: a `continue`, default branch, swallowed timeout or fallback value that loses data without a trace. Why: data loss nobody notices.
- **bounded-attributes**: Span names, metric names and metric labels take bounded values: route templates, not URLs; an enum reason, not an error message. Ids belong on span attributes and logs, never in a span name or metric label. Flag: user ids, ids inside URLs, free text or raw input as a metric label or span name. Why: cardinality blows up cost and queries.
- **alertable-signal**: A new dependency, queue, job or money or auth path emits what an alert needs to isolate it: outcomes counted by a bounded result or reason, a duration histogram, and for queues and jobs the lag or last success. Flag: a new integration whose failures show up only as a generic 500, a job nobody would notice had stopped. Why: no one can page on it, so no one is paged.
- **feature-signal**: A change meant to move a user outcome emits the event or metric that shows whether it did. Flag: a new user-facing flow with no event or metric. Why: no one can tell it works.
- **telemetry-contract**: Span names, attribute keys, metric names and labels, and event names are a contract that dashboards, alerts and queries read. Flag: a renamed or removed name or key with no note of what reads it, a unit changed under the same metric name. Why: the dashboard goes quiet and nobody notices until the incident.
- **safe-telemetry**: Telemetry can neither take the app down nor lose what it buffered. Initialisation runs once, at startup, before the code it instruments, and an exporter or backend failure never throws into a request. The process flushes on shutdown, and short-lived work (serverless handlers, workers, CLIs, scripts) flushes before it exits. Every deployable sets its service name, version and environment from configuration. Flag: telemetry initialised inside a request or module that loads late, `process.exit` with no flush, a signal handler that does not wait for shutdown, a new deployable with no service name or version, an environment hard-coded per build. Why: the telemetry is missing exactly when the process is dying.
- **telemetry-config**: A change to sampling, exporters, redaction or log level keeps errors and slow requests sampled, keeps redaction on and keeps production at its agreed level. Flag: sampling that can drop error traces, redaction switched off, debug logging enabled in production, an exporter endpoint or key hard-coded. Why: the telemetry a team relied on is gone and nothing says so.

## Fix

- Prefer: the repository's existing logger, tracer and metrics helpers, found in code next to the change.
- Never touch: telemetry configuration, exporters, sampling or vendor setup.
- Escalate: adding a logging, tracing or metrics dependency or vendor, any rule where the repository has no logger or tracer yet, and `telemetry-config` and `telemetry-contract` breaks: they are the team's calls.
